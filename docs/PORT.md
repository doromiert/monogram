## Scope retained

This is a port of the official Telegram Android source, retaining its chat interface, with removal of proprietary dependencies in progress. It must not depend on Telegram accounts, API credentials or servers. Local Telegram data structures may remain as UI/storage adapters. A successful protocol-library test is not evidence that the Android app works.

The requested end state includes an installable branded Monogram Android client, working Jabber login and messaging, interoperable OMEMO with persistent keys and visible trust decisions, and an optional deployable helper for Telegram-specific functionality. Basic XMPP must work without that helper. The server may run locally for tests; production deployment is not yet ready.

## Protocol decisions

- RFC 6120/6121: XMPP client connections, SASL and mandatory verified TLS. Service identity derives from the user's JID even when connecting through an explicit host.
- XEP-0198, XEP-0280, XEP-0313: stream management, carbons and archive support, negotiated by feature discovery.
- XEP-0184: delivery receipts only, not a claim that the user read a message.
- OMEMO: Smack 4.4.8's `eu.siacs.conversations.axolotl` wire format, commonly called legacy OMEMO. This does **not** implement `urn:xmpp:omemo:2`. Independent client interoperability still needs testing.
- Keys stay in the app-private filesystem; fingerprint decisions are persisted and bound to both JID/device ID and fingerprint. New and changed identities require explicit decisions. Encrypted sends must fail rather than fall back to plaintext or silently omit a recipient device.
- Prefer XMPP extensions for groups, attachments, replies, edits, reactions, bookmarks, avatars and calls; do not duplicate standard features in a proprietary helper.
- The optional Prosody scheduling module is the first helper feature. It stores opaque message stanzas (including encrypted payloads), validates ownership and limits, and has no OMEMO keys. It currently runs on the account's XMPP server; making a separate remote helper work for external Jabber accounts remains open.

## Direct-message archives and carbons (0.2.2)

The transport now carries direction, original delay/MAM timestamps, stanza/origin/archive IDs and decryption availability to Android. Plain and OMEMO carbon copies share this path. Only the authenticated account's server can provide trusted carbon wrappers; contact-forged copies are rejected. Archive IDs are scoped to the account, contact and direction. Protocol references: [MAM](https://xmpp.org/extensions/xep-0313.html), [stable IDs](https://xmpp.org/extensions/xep-0359.html), [carbons](https://xmpp.org/extensions/xep-0280.html).

On connection, Monogram imports the newest page, then pages backward while allowing other worker tasks between pages. It saves each page and its cursor in one transaction. Later connections catch up forward from the saved newest UID before resuming backfill. An expired cursor triggers one reset/requery without deleting local messages. Reconnection now restarts catch-up with a new archive run identifier, preventing an earlier queued run from continuing. Long-running Android background recovery still needs device validation.

Database schema 3 preserves existing message/peer IDs and text, adds ID aliases and millisecond timestamps, and orders equal-timestamp archive messages by page sequence. Client stanza-ID aliases include the sender resource so different devices can reuse an ID; migrations preserve the earlier unscoped aliases until matched. Original archive timestamps correct previously stored arrival times. Already known plaintext survives undecryptable archive replays; unknown ciphertext gets `Encrypted message unavailable on this device`. A later successful decryption updates that same row. This cannot recover messages that were never encrypted for the device's keys.

## File transfers (0.2.3)

The photo/document send path now uses discovered [XMPP HTTP File Upload](https://xmpp.org/extensions/xep-0363.html) services. Both upload and download require HTTPS with normal certificate/hostname verification. Upload slots enforce the advertised server limit and a client limit of 100 MiB, allow only the specified slot headers, and never redirect an authenticated PUT. Downloads validate redirect URLs, bound streamed bytes, and support cancellation.

Encrypted transfers follow the documented [XEP-0454](https://xmpp.org/extensions/xep-0454.html) format: AES-256-GCM, a random 12-byte IV, and the authentication tag appended to the ciphertext. The IV/key fragment travels inside the OMEMO message and is stripped from HTTP requests. Plain transfers use XEP-0066 out-of-band references. Sending never falls back from encrypted to plaintext. Captions are separate normal chat messages after a successful file send; full durable outbox handling remains unfinished.

Schema 4 retains messages and adds attachment references, verified local paths and serialized media metadata. Files stay under the account's private attachment cache. Incoming files initially offer a download action; authenticated image bytes become native photo previews with their actual dimensions. Secret URLs are removed from rendered message text and browser link handling. Downloads use a temporary file and replace the destination only after size/authentication checks; failure or cancellation preserves an earlier verified copy. Sent-photo locations also resolve to this private cache. The new FileProvider files path exposes only the attachment directory.

The local integration checks include plain/encrypted HTTPS round trips through Prosody, OMEMO URL secrecy, independent SunJCE decryption, server-size rejection, initial and in-flight cancellation, and wrong-key preservation/partial-file cleanup. Android SQLite tests cover schema 1/2/3 upgrades, encrypted archive references, real bitmap preview dimensions and reopening media metadata. These checks do not establish independent-client exchange or complete picker/progress/retry/viewer behavior. Scheduled media, expiring media, replies, paid media, and video that requires conversion explicitly report unavailable rather than using the Telegram upload path.

XMPP presets remain local; no Telegram account or settings service is contacted. There is no separate Monogram auto-download page or configuration.

The transport passes HTTP content type and plaintext file size to the native policy before reading the body. Encrypted files subtract the 16-byte authentication tag when evaluating a limit. The configured size remains an enforced stream bound, capped by the transport's existing 100 MiB maximum. Unknown-size files stay manual. Setting/network changes cancel queued or active automatic jobs and re-evaluate recent history; manual transfers use the normal manual path. Connection-close/error callbacks update Android's state. [XMPP pings](https://xmpp.org/extensions/xep-0199.html) check idle connections every 120 seconds; a failed ping follows the same error/reconnect path as a failed TCP stream. Reauthentication restores OMEMO setup, carbons and presence before Android resumes archive synchronization. Android retries a dead session with a bounded delay. In 0.2.9, manual **XMPP connection → Reconnect** moves from the chat header/title to the home chat-list header when disconnected; Settings also retains the connection page.
