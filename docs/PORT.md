## Scope retained

This is a port of the official Telegram Android source, retaining its chat interface, with removal of proprietary dependencies in progress. It must not depend on Telegram accounts, API credentials or servers. Local Telegram data structures may remain as UI/storage adapters. A successful protocol-library test is not evidence that the Android app works.

The requested end state includes an installable branded Monogram Android client, working Jabber login and messaging, interoperable OMEMO with persistent keys and visible trust decisions, and an optional deployable helper for Telegram-specific functionality. Basic XMPP must work without that helper. The server may run locally for tests; production deployment is not yet ready.

## Protocol decisions

- RFC 6120/6121: XMPP client connections, SASL and mandatory verified TLS. Service identity derives from the user's JID even when connecting through an explicit host.
- XEP-0198, XEP-0280, XEP-0313: stream management, carbons and archive support, negotiated by feature discovery.
- XEP-0184: delivery receipts only, not a claim that the user read a message.
- OMEMO: Smack 4.4.8's `eu.siacs.conversations.axolotl` wire format, commonly called legacy OMEMO. This does **not** implement `urn:xmpp:omemo:2`. Independent client interoperability still needs testing.
- Keys stay in the app-private filesystem; fingerprint decisions are persisted and bound to both JID/device ID and fingerprint. New and changed identities require explicit decisions. Encrypted sends must fail rather than fall back to plaintext or silently omit a recipient device.
- Prefer XMPP extensions for groups, attachments, replies, edits, reactions, bookmarks, avatars and calls; do not duplicate standard features in a proprietary helper.
- The optional Prosody scheduling module is the first helper feature. It stores opaque message stanzas (including encrypted payloads), validates ownership and limits, and has no OMEMO keys. It currently runs on the account's XMPP server; making a separate remote helper work for external Jabber accounts remains open.

## Direct-message archives and carbons (0.2.2)

The transport now carries direction, original delay/MAM timestamps, stanza/origin/archive IDs and decryption availability to Android. Plain and OMEMO carbon copies share this path. Only the authenticated account's server can provide trusted carbon wrappers; contact-forged copies are rejected. Archive IDs are scoped to the account, contact and direction. Protocol references: [MAM](https://xmpp.org/extensions/xep-0313.html), [stable IDs](https://xmpp.org/extensions/xep-0359.html), [carbons](https://xmpp.org/extensions/xep-0280.html).

On connection, Monogram imports the newest page, then pages backward while allowing other worker tasks between pages. It saves each page and its cursor in one transaction. Later connections catch up forward from the saved newest UID before resuming backfill. An expired cursor triggers one reset/requery without deleting local messages. Reconnection now restarts catch-up with a new archive run identifier, preventing an earlier queued run from continuing. Long-running Android background recovery still needs device validation.

Database schema 3 preserves existing message/peer IDs and text, adds ID aliases and millisecond timestamps, and orders equal-timestamp archive messages by page sequence. Client stanza-ID aliases include the sender resource so different devices can reuse an ID; migrations preserve the earlier unscoped aliases until matched. Original archive timestamps correct previously stored arrival times. Already known plaintext survives undecryptable archive replays; unknown ciphertext gets `Encrypted message unavailable on this device`. A later successful decryption updates that same row. This cannot recover messages that were never encrypted for the device's keys.

Incoming files initially offer a download action; authenticated image bytes become native photo previews with their actual dimensions. Secret URLs are removed from rendered message text and browser link handling. Downloads use a temporary file and replace the destination only after size/authentication checks; failure or cancellation preserves an earlier verified copy. Sent-photo locations also resolve to this private cache. The new FileProvider files path exposes only the attachment directory.

Late metadata must not reuse old URL-only bytes or a stale preview. Old files remain intact. Malformed or URL-mismatched persisted descriptions are unavailable, rather than falling back to an unchecked download. Downloads check size and supported SHA-256, SHA3-256 and BLAKE2b-256 hashes before replacing their destination. Uploads copy the selected file into a bounded private snapshot, upload that snapshot with the original filename, describe the same bytes and atomically move them into the cache. Cancellation, a shrinking input and failed copies clean temporary snapshots. Caption rendering removes browser URL spans overlapping `aesgcm` URIs while preserving the displayed text and unrelated web links.

All 28 core tests pass (`.state/captions-integrity-core-tests.log`), including actual local Prosody/TLS uploads after mutating the original file, complete plain caption stanzas, MAM/carbons, independent-provider file decryption and integrity-failure preservation. All 14 Robolectric/API 36 tests pass (`.state/captions-integrity-database-tests.log`), including native image binding before download, invalid metadata, same-URL/different-hash isolation, schema migration, serialization, replay, replies and the 0.2.12 editor/history regressions. The controller networking tests use scripted responses; the core transport tests use the disposable Prosody fixture. No real-contact messages, trust changes or phone navigation were performed.

Private captions are still unfinished. The legacy encrypted-file path retains its separate encrypted text send. [XEP-0384 0.9.1](https://xmpp.org/extensions/xep-0384.html) defines the modern `urn:xmpp:omemo:2` protocol with an [SCE envelope](https://xmpp.org/extensions/xep-0420.html); the caption, file source/key, metadata and fallback elements belong inside that encrypted content. The checked Monocles source follows that shape in `AxolotlService.encryptOmemo2`, while its legacy path carries only the file URL. The existing Smack 4.4.8 legacy backend cannot provide this merely by changing namespaces. Modern support still needs a protocol-compatible engine, separate durable key/session/trust storage, authenticated SCE address validation, migration of previously misclassified unsupported messages and independent-client exchange tests. [Dino's libomemo-c](https://github.com/dino/libomemo-c) is a source-available candidate with the modern ratchet/signature/protobuf changes; the subsequent `modern-omemo` branch selects this ratchet layer and records its narrower component verification below.

No caption APK has been built, published or sent. The latest shipped APK remains 0.2.12; schema 8 and the draft caption work have only been exercised in disposable local tests. Full picker/viewer/touch verification, modern encrypted-caption interoperability and media editing remain pending.

## Modern OMEMO ratchet and durable records (development)

`modern-omemo` builds on `media-captions` and retains the 0.2.12 fixes. It pins [Dino/libomemo-c](https://github.com/dino/libomemo-c/tree/1f0b37fee3ebefc46c32f882623481899a1ba568) through Nix and adds an OMEMO2-only JNI backend. This uses the library's modern internal protocol version 4, raw Ed25519 identity and X25519 prekey encodings, compatible signatures and modern protobuf ciphertext. It does not change the existing Smack legacy identity store, devices or trust decisions. The native boundary rejects missing/changed identity pins, including an Ed25519 sign-bit change that would otherwise map to the same Montgomery key. Ordinary ratchet messages require the exact identity previously bound to that session. Bundle signatures with legacy sign-bit encoding are rejected. Prekey identifiers accept the full unsigned 32-bit range, including zero; our own generated identifiers use positive Java integers.

The JNI store contract is one atomic transaction: commit before exposing a ciphertext, and discard every callback write on error. `MonogramOmemo2Store` implements it with a separate SQLite database under Android's no-backup directory, using full synchronization. Record keys include the local bare JID/device, record type and remote bare JID/device. No legacy trust is imported. Changing/removing a trusted key invalidates only that modern device's session and bound identity, in the same transaction. The new store is not opened by ordinary app startup yet.

The host backend builds against Nix OpenSSL; the arm64 backend reuses the app's existing BoringSSL archive and builds for Android API 23 with 16 KiB ELF load alignment. Symbol visibility/version scripts expose only the six intended JNI entry points, so native crypto symbols do not collide with other modules. Main Android CMake configuration accepts the added target. R8 rules retain the JNI names, failure constructor and Java store callback methods. Complete APK assembly/minification and device execution have not been checked for this development branch.
