# Daily encryption selection

Automatic selection is enabled by default for each contact and MUC. On the first new text/media/location send after the cached result expires, Monogram checks OMEMO 2, then legacy OMEMO, then selects plaintext if neither encrypted mode is usable. Results are stored for 24 hours per account JID and conversation JID, including rooms, and survive app restarts. There is no timer, all-contact scan, scheduled wakeup or background daily job.

The encrypted checks use the actual encryption preparation code with a short local check body, then discard the result. They may fetch public keys and prepare sessions, but never transmit a probe chat message or upload the user's attachment. Outgoing ratchets advance normally, so the next real packet uses fresh state; the discarded ciphertext is not reused. Room checks retain membership validation and the existing unavailable-device policy. OMEMO 2 MUCs are not implemented in Monogram yet; that candidate is currently unavailable, followed by the legacy room check.

Unsupported protocols, unusable encryption material, missing/untrusted devices and explicit key-access denials can fall through to the next mode. Trust is not changed or automatically approved. Connection loss, network timeouts, storage errors, interrupted operations and room membership races abort the check instead of selecting plaintext. The selected mode is committed before the real message or attachment upload. No already transmitted or ambiguously failed message is retried under a weaker protocol, avoiding duplicate or accidentally exposed retries. A cached result is reused until expiry; subsequent ordinary send failures keep their existing error/retry behavior.

Encrypted selection changes have no toast, dialog or confirmation. When plaintext is selected, the current conversation shows a native bulletin saying it is sending without end-to-end encryption. It is limited to once per conversation per 24 hours. If a queued message sends while another screen is open, its warning remains pending until the user opens that conversation while the plaintext result is current. This does not add notifications for encrypted protocol selection.

Conversation security includes **Choose encryption automatically**. Explicitly choosing a protocol or manually toggling encryption disables automatic selection for that conversation. Enabling automatic selection again invalidates its cache, so the next send checks the full chain again. Account/connection/setting changes during a check prevent its result being committed. Offline queued sends wait for a connection as before; attachments are checked before upload and retain the selected mode throughout it.

Validation for 0.2.134: five focused core cases cover candidate ordering, modern success, legacy and plaintext fallbacks, inaccessible keys, and fatal connection/storage/timeout/membership failures (including wrapped I/O errors). Three Android policy cases cover persistence, expiry/clock rollback, independent account/contact/MUC scopes, manual override/re-enable invalidation, actual send-mode preferences and plaintext-warning throttling. Nix arm64 packaging passes. Real phone protocol changes, incoming-client interoperability, UI bulletin placement and a room first-send check remain unverified; no messages were sent during delivery.
